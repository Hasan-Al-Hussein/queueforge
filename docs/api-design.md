# QueueForge API design

## Scope and base addresses

QueueForge exposes two tenant-scoped transports backed by the same application services:

- REST commands and operational resources under `/api/v1`.
- Bounded GraphQL compositions at `/graphql`.

Local defaults are `http://127.0.0.1:3001/api/v1` and `http://127.0.0.1:3001/graphql`. OpenAPI UI and schema JSON are available only outside production at `/api/docs` and `/api/docs-json`. GraphQL introspection and GraphiQL are also disabled in production.

REST owns lifecycle commands, idempotency headers, signed raw-body webhooks, administrative resources, and explicit status codes. GraphQL owns dashboard/catalog/detail composition and calls the same request/approval services for its two mutations. The rationale is recorded in [ADR 0002](adr/0002-api-split.md).

## Authentication and tenant context

1. `POST /api/v1/auth/login` accepts email and password after validating the exact configured web origin.
2. The response contains a short-lived access token, CSRF token, memberships, and selected tenant. The browser keeps the access token in memory.
3. The server sets an opaque HttpOnly refresh cookie at `/api/v1/auth` and a readable CSRF cookie. Both are `SameSite=Lax`; `Secure` follows `COOKIE_SECURE`.
4. `POST /api/v1/auth/refresh` requires the configured Origin, refresh cookie, CSRF cookie, and matching `X-CSRF-Token`. It rotates the token inside a locked refresh family.
5. Authenticated browser requests send `Authorization: Bearer <access-token>`. The API revalidates the current session family and current membership instead of trusting stale role data alone.
6. `POST /api/v1/auth/tenant-select` switches only to an authorized membership and returns a new access session. The action is CSRF-protected and audited.

Login and refresh are limited to 10 requests per minute per throttle identity. The global default is 300 requests per minute; request submission is limited to 60 per minute and inbound webhooks to 120 per minute.

The client must not use `localStorage` or `sessionStorage` for bearer or refresh tokens. The seeded browser demonstration uses users.

### API clients

A tenant/platform administrator user can list, create, and revoke tenant API clients under `/api/v1/api-clients`. Creation returns the full key exactly once; later list/revoke responses never contain secret material. QueueForge stores a domain-separated HMAC-SHA256 of the secret rather than the raw credential.

The credential format is generated by the server and binds tenant UUID, public key ID, and random secret:

```text
<tenant-uuid>.qf_<24-hex-characters>.<43-character-base64url-secret>
```

Send it as:

```http
Authorization: ApiKey <credential>
```

The guard derives tenant context from the verified credential; a caller cannot select another tenant. API clients are limited to `viewer` or `operator`, cannot create/revoke API clients, and are rejected immediately after revocation. Treat the one-time response as a password: do not log, commit, screenshot, or store it in browser storage.

API-client creation requires durable idempotency. The first committed response is `{ client, apiKey, replayed: false }`; a replay deliberately returns `{ client, apiKey: null, replayed: true }` instead of revealing the credential again. If the connection fails before the one-time secret is received, replay to identify the committed client, revoke it, and create a replacement with a new key.

## Authorization model

| Role             | Server-enforced capability summary                                                            |
| ---------------- | --------------------------------------------------------------------------------------------- |
| `viewer`         | Read tenant workflows, requests, dashboard, and permitted personal notifications              |
| `approver`       | Viewer reads plus list/decide approvals; does not inherit operator commands                   |
| `operator`       | Submit/cancel/retry requests, inspect operations/webhooks, replay deliveries and dead letters |
| `tenant_admin`   | Workflow, webhook, membership, audit, and operational administration                          |
| `platform_admin` | Create tenants and perform tenant-admin actions after an audited selection                    |

API clients are restricted to viewer or operator scope. Permission-aware UI controls improve clarity but never replace the server policy. Cross-tenant object lookup is tenant-scoped and should not disclose whether another tenant owns an identifier.

## Common request rules

### Correlation

Clients may send `X-Correlation-Id` as a UUID. The API accepts a valid value or creates one. That transport value is authoritative; submission bodies and GraphQL arguments do not override it. Every HTTP response exposes `X-Request-Id` and `X-Correlation-Id`; the same correlation ID propagates through the transaction, outbox event, BullMQ job, attempts, webhook, notification, and audit history.

### Idempotency

Routes marked with a key requirement validate `Idempotency-Key` against `[A-Za-z0-9._:-]{8,200}`. Durable HTTP idempotency is implemented for workflow and API-client creation; request submission, cancellation, and retry; approval decisions; webhook-endpoint creation and delivery replay; and tenant and membership creation. Those commands store only a key hash and bind it to tenant, endpoint scope, principal, operation, and canonical payload fingerprint.

For a durably bound command, an identical replay reuses the completed record and returns either the recorded response or the same committed resource identity without repeating the effect; a different fingerprint returns `IDEMPOTENCY_KEY_REUSE`. API-client and webhook-endpoint creation replays omit their one-time secrets, while approval replay reports `{ "replayed": true }`. Only REST request submission currently exposes `Idempotency-Replayed: true`; clients must not infer that header is available on every command.

Clone draft atomically returns or creates the current draft without using an idempotency key. Activation and dead-letter retry likewise do not require or bind a key; a repeat is evaluated against the new domain state and may conflict or fail. These state-based commands are not successful durable HTTP replays.

### Body and query limits

- Default REST and GraphQL body guard: 256 KiB.
- Inbound signed webhook body guard: 1 MiB.
- Express JSON parser ceiling: 1 MiB; URL-encoded ceiling: 64 KiB.
- REST pagination: `page >= 1`, `1 <= pageSize <= 100`; defaults are 1 and 25.
- GraphQL pagination: `pageSize <= 100`.
- GraphQL: depth 8, list depth 3, calculated complexity 200, and 20 aliases.

Paged REST responses use:

```json
{
  "items": [],
  "meta": {
    "page": 1,
    "pageSize": 25,
    "totalItems": 0,
    "totalPages": 0
  }
}
```

## REST route map

All business routes except login, refresh, health, and inbound webhooks pass through the authentication guard. Guarded business routes accept a bearer access token or an `ApiKey` credential subject to the principal's role. Session lifecycle and user-only administration still require a compatible user session. Metrics bypass the session/API-key guard and apply their own `METRICS_TOKEN` bearer check in production.

### Membership creation

`POST /team/memberships` accepts `email` and `role`. If the email already identifies a user, `displayName` and `initialPassword` may be omitted. For a new identity, supply both; `initialPassword` must be 12-256 characters. The server hashes it with Argon2id and never returns it.

## GraphQL operation map

| Operation                                                                               | Shape and purpose                                                |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| `dashboardOverview` query                                                               | Status counts, queue health, recent requests, throughput buckets |
| `workflows` query                                                                       | Workflow catalog                                                 |
| `workflowRequests(page, pageSize, status)` query                                        | Bounded tenant request list                                      |
| `requestDetail(id)` query                                                               | Request plus transitions and optional approval composition       |
| `submitWorkflowRequest(workflowKey, payload, idempotencyKey)` mutation                  | Same application submission path as REST                         |
| `decideApproval(approvalId, decision, expectedRevision, note, idempotencyKey)` mutation | Same approval path as REST                                       |

Application/resolver failures pass through QueueForge's shared exception mapping. An Apollo error-envelope plugin then normalizes every GraphQL failure—including parse, schema-validation, coercion, and query-limit errors—to the bounded public code vocabulary in `extensions` and adds `requestId` and `correlationId`. Stack traces are not returned.

## Error contract

REST errors use the shared envelope:

```json
{
  "error": {
    "code": "STALE_REVISION",
    "message": "The draft revision changed",
    "details": {}
  },
  "requestId": "00000000-0000-4000-8000-000000000000",
  "correlationId": "00000000-0000-4000-8000-000000000000",
  "timestamp": "2026-08-24T12:00:00.000Z"
}
```

Common statuses include 400 request validation/idempotency-required, 401 authentication/signature, 403 authorization/CSRF, 404 tenant-scoped not found, 409 conflict/stale revision/replay, 413 body limit, 422 active-workflow payload-schema validation, 429 rate limit, and 503 dependency unavailable. The durable submission record preserves a 422 validation result for an identical replay. Unhandled failures return a generic `INTERNAL_ERROR` without a stack or secret.

## Webhook contracts

Inbound and outbound header spelling, canonical signature bytes, stable event identity, clock rules, and compatibility policy are documented in [event contracts](event-contracts.md). The end-to-end retry and recovery path is in [event flow](event-flow.md).

Endpoint creation returns `{ endpoint, signingSecret, replayed: false }` on the first committed response. An idempotent replay returns `{ endpoint, signingSecret: null, replayed: true }`; it identifies the same endpoint without revealing the secret again. If the first response is lost, disable that endpoint and create a replacement rather than trying to recover ciphertext as plaintext.

The bundled local sink is preconfigured only for the seeded endpoint and its startup secret. A newly generated endpoint becomes deliverable only after its receiver is configured with the one-time secret; QueueForge does not silently register arbitrary secrets in the demo sink. Host-first workers target `http://127.0.0.1:3300/webhooks`, while the full Compose worker uses `http://webhook-sink:3300/webhooks`.

## Compatibility policy

- REST additions should be additive within `/api/v1`; breaking changes require a new version.
- Event envelope breaking changes require a new `schemaVersion` and consumer migration.
- GraphQL fields may be added, but existing field meaning must not change silently.
- Both transports must continue to call shared application services for authorization, state transitions, idempotency, audit, and outbox behavior.
- OpenAPI/schema generation is implementation evidence, not a substitute for contract and authorization tests.
